# SFP 开机识别 2.5G / 10G：候选新方案（2026-11-06）

> 状态：**全部未实现、未上机**，仅设计归档。当前 main 分支实际使用的是
> `0901-sfp-module-manager.patch`（首脉冲 22 tick）+ `0902-sfp-25g-mode-hysteresis.patch`
> （2.5G 候选模式保持 30 tick），实测 26.09s 上链、pulse=0。
>
> 证据等级标注：〔实测〕= 本机或归档日志实测；〔源码〕= 当前树源码可核对；
> 〔规范〕= SFF-8472 / 802.3 定义；〔推断〕= 尚未验证。

## 0.0 2026-11-07 实测补充（先读这条）

当日对「首脉冲阈值」做了三档对照，结论：**阈值不是杠杆，别再调它**。

| 固件 | `SFP_MGR_BOOT_TICKS` | pulse done | sfp link up |
|---|---|---|---|
| sfpfast | 3 | 29.93s | 56.97s |
| sfp12 | 12 | 39.19s | 56.89s |
| 定版 8bc | 22 | 50.95s | 57.21s |
| v5 重刷（md5 a187820f） | 12 | 33.35s | 57.29s |

- 四组落在 56.9~57.3s，差 0.4s 在噪声内；
- 11-05 记录过的 22.97s，同镜像重刷后为 57.29s，**未复现**，判为单次偶发；
- 热重插仍是 5~6s（模块温热、零 pulse）；
- 冷启动瓶颈是模块**从上电到可协商**的物理时间，pulse 时机、`HOLD_MS`、
  `SFP_25G_MODE_HOLD` 滞回窗口三条路都已试过或已判定无效。

因此下面第 2 节里涉及「改等待/改阈值」的方案预期收益有限；真正还没试的是
2.1（持久化 last-good mode）、1.3（更快读 PCS）、2.2（DDM 就绪判断）。

## 0. 先纠正一个前提

"识别"不是瓶颈。SSDK 第一次 `sfp_read_status`（约 10.7s）就已经从 EEPROM 读到速率编码，
四个固件跨三天实测均为 8~10s 读到 `0x2000`（2.5G）/`0x6700`（10G）〔实测〕。
后面 14~16s 才出 link，是模块自身数据面没起来 + 弹跳副作用。
**所以新方案分两类：更准的判据、更少的等。**

## 1. 判据类

### 1.1 A0h byte12 单字节判定有洞

- 〔源码〕`src/hsl/phy/sfp_phy.c:530-533` 只读 A0h `SFP_SPEED_ADDR=0xc`，
  取高字节 `SFP_TO_SFP_SPEED=(reg>>8)&0xff`，再按阈值分档：
  `SFP_SPEED_1000M=10 / 2500M=25 / 5000M=50 / 10000M=100`（`include/hsl/phy/sfp_phy.h:29-34`）。
- 后果：华为 MA5671A 这类自报 1G 的猫棒，byte12 = `0x0D` → 落进 1G 分支
  → 配 1000BASE-X，永远不上 2.5G。〔规范〕SFF-8472 byte12 是 "nominal bit rate"，
  厂商填法不统一，不能当唯一判据。
- 改法：byte12 + byte6（`SFP_TYPE_ADDR 0x6`，以太网兼容码）+ 厂商名联合表；
  `byte12 ∈ [0x0D, 0x20]` 且 byte6 不是 `1000BASE-T(0x08)` 的模块，
  第一候选直接给 2500BASE-X。详见 `docs/sfp-onu-1g-modules.md`。

### 1.2 弹跳其实有一个开关能直接关掉

- 〔源码〕`sfp_phy.c:56-62`：`pdev->autoneg` 由 `PHY_F_SFP_SGMII` 这个 feature 决定，
  只有 1000BASE-T 电口模块会置位；`sfp_phy.c:578-586`：2.5G 分支在
  `autoneg == AUTONEG_DISABLE` 时**直接返回 `PORT_SGMII_PLUS`**，不执行模式交替。
- 也就是说：把光纤模块的 `PHY_F_SFP_SGMII` 清干净，`23↔4` 弹跳路径整体不执行。
  这比 0902 的迟滞更根本（0902 是"弹之前多等 30 tick"，这条是"根本不弹"）。
- 建议与 0902 做单变量对照验证，不要一次改两处。

### 1.3 PCS 状态可以读得比 1 秒更快

- 〔源码〕`sfp_port_status_get_from_uniphy()` 对 10G 直接读
  `sr_xs_pcs_kr_sts1.plu`；2.5G 走 UNIPHY channel0 register。
- 〔源码〕1s/tick 只是 `mac_sw_sync_task` 的软件节流，硬件 PCS 状态是实时的。
  可以 100~200ms 轮一次做早退，把"发现延迟"从秒级压到百毫秒级。

## 2. 策略类

### 2.1 持久化 last-good mode（性价比最高）

- 把上次成功 link 的 interface mode 写盘，开机第一个 poll 直接套用，
  验证窗口缩到 2~3 tick。
- 〔实测〕30 轮软重启 `enc=0x3 / br=0x20` 30/30 完全一致 —— 模块身份跨重启稳定，
  没有"每次重猜"的必要。
- 落盘位置现成：`/dev/mmcblk0p24` 是 1GiB ext4（rootfs_data），目前 `enabled 0`，
  overlay 还走 tmpfs。启用它顺手解决"运行时装的应用重启即丢"。
- 风险：换模块后第一次启动会走一次错档，需要 3 tick 内失败回退。

### 2.2 用 DDM 判"模块就绪"，替代固定 22 tick

- 〔实测〕阈值曲线非单调：12 tick → 38.65s，22 tick → 26.09s。
  说明 22 不是"等够了"，而是"刚好躲开打断点"——早 pulse 会把 SerDes 训练打断。
- 改法：读 A2h `96-97`（RX power）、`100-101`（TX bias），读到有效值再 pulse。
- 缺口：〔源码〕SSDK 只有 A0h(`0x50`) 与 `0x56` 两个地址的封装
  （`sfp_phy_i2c_read`），A2h(`0x51`) 需自加读取函数，约 30 行。

### 2.3 按模块类别分档等待

- 10G 是真光模块、无 AN 训练 → 首 pulse 给 2~4 tick；
- 2.5G 猫棒要等自身 SoC boot → 保持 22；
- 读不到 / 编码不认识 → 12 兜底。
- 依据：第一次 poll 就知道是哪类〔实测〕，等待策略没必要一刀切。

## 3. 已排除，不要再花时间

| 想法 | 排除依据 |
|---|---|
| 补 `sfp_tx_dis_pin` 让 pulse 真正生效 | ER2 笼子 DTS 无该引脚，`sfp_phy_tx_dis_status_set` 恒返回 `-19`〔实测〕 |
| 双 PCS 并行监听两种速率 | 每口只有一个 UNIPHY 实例，硬件上不存在〔源码〕 |
| 调首脉冲阈值（3 / 12 / 22 tick）换启动速度 | 四档实测均 56.9~57.3s，差 <0.5s；瓶颈在模块上电到可协商的物理时间〔2026-11-07 实测〕 |
| 在 uboot 预读 EEPROM 传给内核 | 内核 10.7s 才 init SFP，但 EEPROM 本来就读得到（插槽独立供电），不是读不到的问题〔实测〕 |

## 4. 建议验证顺序

1. 2.1 持久化 mode —— 风险最低、收益确定（26s → 3~5s 量级）；
2. 1.2 + 2.3 一起改（各几行），一次覆盖 10G / 2.5G 两条路；
3. 2.2 DDM 就绪探测单独一版，不与其它变量混；
4. 1.3 早退放最后，属体验优化。

判据仍是三项同时成立且各复现 ≥2 次：热插拔 ✅ / 断电重启 ✅ / 10G ✅。
