# 文档与结论的写法规范

这份规范只解决一件事：**别让没验证过的东西看起来像已验证过。**

起因是 2026-11-06 那次排查里的两次翻车：

- README 里写「光口↔电口数据面未打通」，实际那个现象是第三方 ImmortalWrt 固件
  （VIKINGYFY 版）测出来的，代码层依据只是上游邮件列表的讨论。本仓库这版从没
  做过跨口实测，而 `eth0` 的收发计数是 710/784 包、零错误——写成了既成事实，
  但本机根本没验证过。
- README 里写「pcie0 打开会报 Failed to find NVMEM device」，把 `fw_printenv`
  的输出误挂到 PCIe 头上，真正的 pcie0 失败现象（probe 起不来、没有
  `PCI host bridge to bus 0000:00`）反而没写。

同一个毛病：**把别处的结论、或同一台机器上另一条日志，直接当成本问题的答案。**

## 一、三档标注

任何结论性描述，必须能归到下面某一档，并在文字里体现出来：

| 档 | 含义 | 写法 |
|---|---|---|
| **已实测** | 在本仓库构建的固件上跑过，有命令和输出 | 直接陈述，附命令与关键输出片段 |
| **待复测** | 有理由怀疑，但没有本机证据 | 明确写「未复测」+ 现有迹象（计数、日志）不足以定论 |
| **有来源** | 来自上游邮件列表、第三方固件、归档文档 | 写出处（谁、什么时候、哪份文档），并说明「不是本仓库实测」 |

不允许出现的写法：「未打通」「不支持」「必然失败」——除非是本机实测并附了输出。

## 二、写进 README 的硬门槛

`README.md` 的「已知限制」小节，每一条必须满足：

1. **现象**：本仓库固件上的真实输出，带时间戳或命令
2. **已排除项**：实际试过、实际否掉的，不是「应该不是」
3. **当前状态**：还能不能做、缺什么条件

缺任何一项，就不进「已知限制」，改放 `docs/` 下作为排查记录，标题里注明「未复测」。

## 三、引用外部结论的写法

引用上游邮件列表、别的固件、旧归档，一律这样写：

```
> 来源：<谁/哪个项目>，<时间>，<链接或文档路径>
> 该结论来自 <固件名/分支>，与本仓库版本不同，未在本机复测
```

反例（本次出问题的写法）：

```
- 光口↔电口数据面未打通：上游 qcom_ppe 对 host-bound RX 有未完成的 gap
```

看似权威，实际上把「别人的现象 + 别人的代码分析」压缩成「我们的结论」。

## 四、提交信息里带证据

结论性提交（改 README 的已知限制、改文档结论）要在 commit message 里附：

- 触发问题的命令
- 输出里的关键行
- 判断依据（为什么排除其他可能）

例：

```
串口实测：
[ 3.321734] qcom-pcie 18000000.pcie: Phy link never came up (LTSSM=0x3 ...)
0x3 = POLLING_COMPLIANCE -> 发送侧已起，收不到对端训练序列
```

## 五、过时结论要及时改

上游变了、驱动换了、验证过了，就当场改掉，不留「历史正确」。旧结论要么删除，
要么移进 `docs/` 并在开头写明「已被 <提交号> 推翻，保留供追溯」。

## 六、与本规范相关的一次自查清单

写任何一段技术结论前，问自己四句：

1. 这台机器上我亲眼看过了吗？
2. 我引用的是谁的话？他测的是哪个固件？
3. 这条日志的打印者是谁？（是那个子系统吗，还是别人凑巧在同一时刻打的）
4. 如果结论错了，别人能不能从当前描述里看出来我没验证？
