# 2.5G 猫棒 SFP 口：测试经验总结（2026-11-05）

## 一、踩过的错误结论与纠正依据

| 错误结论 | 当时依据 | 纠正依据 |
|---|---|---|
| 关掉日志（log_level=0）就能救首启 | 热插拔后设 0，抖动冻结 | 冷启动 138s 仍 down；0 级只是不放大问题，不是修复 |
| 2 级日志必然失败 | v4 之前 2 级实测失败 | v2a 基线默认 2 级、404s 自恢；当时是 3 级折腾 124 次后状态机已卡 |
| "pulse 1/2、pulse 2/2 已发出，兜底生效" | INFO 打印了 pulse 字样 | `tx_dis_status_set` 恒返回 -19，MAC/PCS 重启从未执行，是死代码 |
| SFP LED 可作链路判据 | 拔插时灯灭灯亮 | DTS tl90m36 + UCI netdev 软件灯，跨固件不成立 |
| 首启 404s 起来 = 已修复 | 最终 link 2500 | 那是碰运气自愈；热插拔 83s、v3 195s 失败都证明不确定 |
| 刷完 sysupgrade 就生效 | 重启后设备回来了 | `platform.sh` 无 jdcloud,er2 分支，只重启不写盘；ko 大小未变、DEFAULT_LEVEL 未变 |

## 二、有效方法（应固化为流程）

| 方法 | 说明 |
|---|---|
| 在失败现场做实验 | 不重启、不刷机，用 `sfp_force_mode` + `sfp_kick` 逐模式扫，一次拿到答案 |
| 判据用计数不用状态 | `carrier_changes` 连续 60s 不增长；`rx_bytes/tx_bytes` 必须有增量 |
| 1 秒粒度采样 | 8.3s 周期的 flap 只有细粒度能抓到；15s 采样会整段漏掉 |
| 时序对齐 uptime | 设备墙钟回跳，日志按 boot_id 命名 |
| 单变量 | 一次只改一处，否则不知谁修好的 |
| 确认改动真的进了镜像 | 核对 ko 大小 + `strings` 里的新字符串 + 反解 squashfs 里的脚本默认值 |
| 每次全量抓取归档 | dmesg / logread / cmdline / 接口状态 / RateEncode / sfp-detect 时间线 |

## 三、回归测试最小集（每次改 SSDK 后必跑）

| 步骤 | 判据 |
|---|---|
| 1. 冷启动（factory 刷写后） | 180s 内 link 2500 |
| 2. 软重启 ×2 | 每轮 180s 内 link 2500；允许 12tick 弹跳，禁止无休止 flap |
| 3. 13 分钟静置 | carrier_changes 冻结，dmesg 无 Link down |
| 4. 热拔出 -> 插入 | 插入后 180s 内恢复 2500 |
| 5. 失败态模式扫描（可选） | 验证恢复动作真的执行（看返回值，不看打印） |

## 四、当前确定性结论

- 冷启动 23.2s；软重启 40.4s / 41.8s（12tick 弹跳 23->4->23，约 4s 后起链路）
- 弹跳期间链路瞬断约 2s，管理面不能放在 SFP 口
- 同模式重复 apply 是空操作，这是此前所有"PCS-only 恢复"无效的根本原因
